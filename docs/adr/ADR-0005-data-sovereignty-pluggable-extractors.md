# ADR-0005：数据主权——自持 schema 与可插拔抽取引擎

- **状态**：已接受
- **日期**：2026-09-17
- **取代**：早期"内核用 GraphRAG/LightRAG"的口头结论（会话裁决，未成文即被本 ADR 修正）

## 背景

候选抽取引擎：Microsoft GraphRAG、LightRAG（港大）、graphify（owner 已实测：DeepSeek 语义
抽取端到端打通，energy-ai-platform 建成 7553 节点 / 22937 边 / 319 社区，成本 $0.49）。
风险事实：研究引擎版本间 API 与存储格式漂移剧烈——GraphRAG 从 v0 到 v1 存储层重构过数轮；
graphify 是工具管线，不是可承诺长期稳定的依赖。

## 决策

1. **自持 schema**：chunk / entity / edge / community 的持久化格式由本项目定义，
   落在 SQLite + parquet（ADR-0003）。
2. **统一 Extractor 接口**：一切抽取引擎实现同一协议，落位 `src/siku/extractors/`，
   作为可插拔后端接入；禁止 import 引擎内部存储模块。
3. **进程隔离**：AGPL 引擎（MinerU）只准子进程方式调用，规避协议传染。
4. **重依赖进 extras**：torch 系（Docling 等）放 `[project.optional-dependencies]`，
   核心安装保持秒级。

## 理由

语料是用户资产，引擎会过时。产品数据层绑定任何一家研究引擎 = 定期被迫重写；引擎可以
全量更换，前提是它只是"过路客"而不是"地基"。graphify + DeepSeek 管线已端到端验证，
直接复用其方法而不绑定其实现。

## 被否选项

- **直接依赖 GraphRAG 库的存储层**：漂移绑定，版本升级即被迫迁移；
- **全自研抽取管线**：丢掉已验证资产，重造轮子；
- **数据层抽象到引擎侧**（让引擎自己存）：事实源失控，违背 ADR-0004 幂等红线。

## 代价与风险

- Extractor 接口是一次性抽象成本，且接口设计可能被第二、第三个引擎打脸——接受，
  打脸即复核信号；
- 子进程隔离带来进程管理与错误传导的工程量。

## 复核信号

接入第三个引擎时接口仍放不下 → 接口设计缺陷，重开本 ADR；某引擎长期成为唯一实际
使用者且无第二引擎需求 → 简化接口，避免抽象税。
