# ADR-0015：实体 join 检索增强通道——SAG 式查询时动态超边

- **状态**：已接受
- **日期**：2026-11-09

## 背景

混合召回（向量 + BM25 + 重排，ADR-0006）覆盖语义相关与关键词精确匹配两类问题，
但存在结构性盲区：**桥接证据**。多跳问题的中间证据往往与查询没有直接词汇重叠
（"A 和 B 怎么产生联系"——中间实体 C 所在段落可能既不含 A 也不含 B 的问法），
两路召回都够不着。同时图谱检索面（`graph_search`/`graph_neighbors`）只返回图结构
（实体/边/社区），不返回原文证据，实体联动问答拿不到可引用出处。

2026-06 论文 SAG（SQL-Retrieval Augmented Generation with Query-Time Dynamic
Hyperedges, arXiv:2606.15971）给出了与本项目约束高度同构的第三条路：把「chunk ↔ 实体」
提及关系做成可 join 的结构化索引，查询时以共享实体为 join key 动态连接证据邻域
（动态超边），证据永远保持原始 chunk 形态、不预建静态图。关键消融证据：

- 收益主体是**确定性 join 替代图传播**（vs HippoRAG 2 的 PPR：MuSiQue R@5
  65.1%→80.0%），超边表示本身只额外贡献 +2.9 分；
- 关闭一跳扩展（H=0）R@5 从 80.0% 跌至 69.4%——扩展贡献的恰是向量召回覆盖不到的
  桥接证据，而非改善排序；
- 检索质量与 embedding 模型解耦（换 embedding 后 SAG 稳定、PPR 方法剧烈波动）——
  join 靠实体身份精确匹配，不靠向量逐跳传播；
- 其自述局限同样关键：种子解析、固定剪枝预算、实体不消歧（下文逐条给出本项目对策）。

现状核对发现：本项目图谱抽取管线**本来就是 chunk 级输入**（`LlmGraphExtractor.extract`
逐 chunk 抽取，缓存键含 chunk 身份），合并后 `Entity.anchors` 已携带 `chunk_id`
（`SourceAnchor`，`graph/models.py`）。**SAG 所需的「chunk ↔ 实体」索引原材料已经在
entities.parquet 中存在，只是从未被检索面消费。**

本项目定位为学习/求职项目：有明确价值且成本可控的能力主动落地，不等需求信号。

## 决策

**新增「实体 join 检索增强通道」——与混合召回、图谱浏览并列的第三检索纪律。**

1. **纯确定性、零模型调用**：种子解析（查询串对实体名的确定性匹配）→ 一跳共现 join
   扩展（种子实体 → 其锚点 chunk → 同 chunk 共现实体 → 共现实体的 chunk）→ 打分
   去重，全部是既有派生物上的读取与集合运算。无模型环境、本地小模型同样可用。
2. **只读既有两份派生物**：图谱 parquet（实体锚点）+ 检索 SQLite 索引（chunk 正文）。
   不新增存储组件、不改索引 schema、不新增 LLM 抽取。两份派生物构建时点错位时，
   过滤索引中已不存在的 chunk 并在结果中如实报告跳过数（截断明示哲学）。
3. **消费面 = MCP 只读工具**（第八个只读工具）：自由文本进、证据 chunk 出，附实体
   溯源（种子/桥接实体）与可审计的空结果分型（无种子命中/扩展为空），沿用 SAG 的
   失败定位哲学与既有归一化错误口径。
4. **主链路不动**：`/api/ask`、`siku search`、golden set 口径全部不变；join 通道以
   独立多跳评测集（「问题 + 桥接证据 chunk」标注对）作为自身质量门禁，在评测集上
   与纯混合召回对照并如实记录。
5. **有界与溯源**：结果带来源锚点可跳回原文；服务端有界查询 + 截断明示，与图谱类
   工具同一口径。

三处明确不照抄 SAG：存储用自持三件套（它用 MySQL + ES 是 web 级生产环境的选择）；
不做每 chunk 的 LLM 事件改写（消融显示非收益主体）；不做 append-only 语义（本项目
`source_hash` 幂等重建与移除消减是更强语义，join 只读派生物、天然跟随重建）。

## 理由（当前实现 vs 本方案）

| 维度 | 现状（不落地） | 本方案（实体 join 通道） |
|---|---|---|
| 桥接证据 | 结构性盲区，两路召回均覆盖不到 | H=1 join 直接取共现邻域，针对性机制 |
| 图谱检索面 | 只出图结构，实体联动问答不可引用 | 实体 → 原文 chunk 证据回链，引用体系零改动 |
| 成本 | — | 零模型调用、零 schema 变更、零新抽取；10⁵ chunk 级内存 join 毫秒级 |
| 兼容性 | — | 既有 spec 行为不变；MCP 面纯增量加工具 |
| 测试 | — | 确定性路线全程可 fake、CI 永不打真实 API |
| 维护 | — | 无独立状态，随两份派生物重建自然更新 |

## 被否选项

- **HippoRAG/GraphRAG 式图传播检索**：消融证明确定性 join 优于 PPR 传播衰减；且
  引擎接入违反 ADR-0005 数据主权，ADR-0006 已否过「GraphRAG 全家桶做检索」。
- **自由 Text-to-SQL 查询面**：Spider 2.0（632 道企业级工作流）上前沿模型仅 ~21%，
  本地 BYOK 弱模型更不可用；且引入 LLM 生成 SQL 的只读执行安全面（ATTACH/PRAGMA
  写、资源限制）。结构化表格域维持 ADR-0004 既有触发器（DuckDB 直查通道，需求点火
  再启），不因本 ADR 改变。
- **直接把 join 通道接进 `/api/ask` 主链路**：主链路 golden set 基线无失败案例驱动；
  改主链路必须过 ADR-0006 回归门禁。先独立成通道积累多跳评测证据，集成是复核信号
  驱动的后续 change。
- **SAG 全量复刻**（LLM 事件改写 + 查询实体 LLM 抽取 + 实体向量扩展 + LLM 重排）：
  各层在消融中均非收益主体或显著抬升成本与延迟；全部列为复核信号升级路径而非首发。

## 代价与风险

- **中文效果待验证**：论文三个基准（HotpotQA/2Wiki/MuSiQue）全为英文。验证方式 =
  本 change 建中文多跳评测集，在其上给出 join 通道 vs 纯混合召回的对照数字；不达
  预期则如实记录，通道保持 MCP 工具面定位（供强客户端自行编排），不进问答编排。
- **确定性种子解析召回上限**：字面匹配覆盖不了词形变化与别称。缓解：复用 merge 后
  稳定 `entity_id` 与 `ambiguous_entity_names` 名单（歧义如实呈现，不静默合并）；
  不足时升级 LLM query 实体抽取（见复核信号）。
- **图谱/索引时点错位**：过滤 + 如实报告跳过数，不做自动补偿（自动维护语义归
  graph-auto-refresh 既有开关管辖）。

## 复核信号

- 多跳评测显示 join 通道显著补盲 → 评估 `/api/ask` opt-in 集成与 WebUI 呈现
  （届时过 golden set 门禁，另开 change）；
- 种子召回成为瓶颈 → 引入 LLM query 实体抽取（few-shot；SAG 消融旁证：结构路径是
  引擎，Kevent=5 时 80.0%、纯语义路径仅 56.2%）；
- 排序（而非召回）成为瓶颈 → 引入 LLM 重排做证据链选择（SAG 消融：换轻量重排器
  R@5 80.0→62.2）；
- 语料达 10⁶ chunk 级（ADR-0003 触发器）→ 重评内存 join 形态。
