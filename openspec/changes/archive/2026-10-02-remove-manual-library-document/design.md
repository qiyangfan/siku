# 设计：单文档确认移除，复用库域清理

## 当前证据与单一结论

当前资料库没有单文档移除端点，purge 从全部 tombstone 出发；普通手动导入文件没有 tombstone。`origin_path=null` 仅是展示字段，不能作为“从未由来源目录管理”的权威证据。现有 `sync_entries` 才持有同步归属。

采用既有清理内核的按来源选择能力，不另建删除子系统。只有服务器认定为手动导入、且没有同步登记引用的来源可移除。来源同步的文档仍走既有登记、扫描、标记与全量确认清理流程。

## D1：准确目标与薄入口

`GET /api/library` 每项增加真实 `source_id` 和服务端计算的 `removable`。UI 不从文件名、路径、hash 展示长度或 `origin_path` 推导是否可移除。判断及执行前复查都基于同一库域登记；任何 `sync_entries` 归属引用都排除手动移除。

新增 `POST /api/library/remove`，请求为 `{source_id, confirmed: true}`，响应与进度查询沿用既有 LibraryJobs 契约。未确认返回 422；不存在返回 404；来源受目录同步管理返回 409 与稳定可行动错误码；同库写入冲突保持 `library_job_busy` 的 409。已确认但未完成的 `user_removed` 标记允许按原 ID 重试。请求不接受文件路径。

CLI 增加薄命令 `siku remove SOURCE_ID --confirm`，调用同一内核，支持既有 JSON/中文错误口径。没有 HTTP/CLI 两套清理实现。

## D2：确认标记与受管文件

用户确认后在现有 tombstone 写入 `reason=user_removed`，不伪装成上游 missing。以来源 ID 解析 attachments、notes 与同 ID 的检疫副本，沿用既有命名/元数据查找。路径须校验位于既定受管根内，不能经符号链接越界；没有客户端任意路径拼接或按名称模糊匹配删除。

为既有 purge 内核增加来源选择参数；原全量 purge 默认行为不变，单项移除仅处理目标 ID，不能顺便清理别人的 missing/superseded。外部手动导入原件和所有来源目录始终只读，删除按钮文案说“从资料库移除”，不说“删除原文件”。

原全量 purge 的处理范围仍是全部已标记来源；遇到 `user_removed` 时必须调用同一完整收尾管线，不能沿旧文件循环提前清掉它的标记或漏掉快照失效。入口不同不能绕过已确认移除的完成条件。

取得写锁后先恢复该库已有的、可验证且已经确认的消减发布，再核对来源与索引完整性；先形成已验证的消减暂存产物，随后才进入不可逆清理及发布。失败保留已确认标记，即使部分文件已删也能根据来源 ID 接续；只在受管文件、索引和可读派生物收尾均完成后移除标记及目标登记。复用文件定位和 tombstone，不另建操作日志表或第二份事实清单。

## D3：索引消减不依赖模型

不能直接调用需要当前 embedding provider 的 `sync_index`。现有同步首先校验当前模型元数据，配置变更或凭证失效时会阻断删除。

复用既有临时索引构建、来源复制、向量行复用、校验与提交一致性机制，增加按 ID 消减的专用入口：读取原索引已存模型/维度/通道元数据，只复制剩余来源的 SQLite document/chunk/FTS5 数据和向量行，形成一致的新提交。不生成新 embedding，不检查当前 BYOK 是否可达，不更换索引模型元数据；空索引也是合法结果。没有既有索引时无需创建模型索引。

现有双产物发布先替换向量再替换 SQLite；两步之间中断仅能被 commit 校验发现，不能自动恢复。因此不能把已有一致性检查当成恢复机制，也不能在重试前无条件删除临时产物。

消减复用临时 SQLite/向量构建，但为已验证暂存对保留同一 commit 凭证与目标来源关联（沿用索引 meta、向量 commit 和已确认 tombstone，不新建日志库）。发布中断后，任何同库写入口先检查该已确认消减：暂存/最终向量与暂存/最终 SQLite 按同一 commit 配对，完成确定的向前发布，再做普通完整性预检。向量已替换而 SQLite 尚未替换时，从保留的已验证暂存 SQLite 完成切换；两者已完成时只接续文件/快照收尾。未经验证的构建半成品不能作为恢复依据，不相关或不能配对的损坏明确失败。

普通索引构建不得清掉尚未完成消减的可恢复暂存对；恢复本身不调用 embedding，不读取当前端点凭证，不自动清理未经确认的来源。既有索引损坏须明确失败；已开始的清理保留标记等待恢复，不能仅删 SQLite 而残留向量或报告半份新索引为成功。原件删除与双索引发布不宣称跨文件系统原子事务，恢复性来自已验证产物、提交凭证与已确认标记。

## D4：同库写入串行，避免旧内容复活

同一真实 vault 使用一个写入边界，覆盖资料库导入、原始 `/api/ingest`、扫描的写入阶段、purge、索引及 graph/wiki 构建，以及改变同步归属的来源启停/解除登记，并覆盖 CLI。同库不同进程也必须互斥，单进程 LibraryJobs 槽不足以保证这一点。

采用成熟轻依赖 `filelock` 的平台文件锁，锁文件放在该 vault 的固定非语料位置；继续复用 LibraryJobs 作进程内状态与反馈，不自写 POSIX/Windows 锁协议或分布式锁。任务获得写入权后保持到全部写入与发布结束，入口统一取锁，内部共享实现不重复抢锁。HTTP/CLI 手动冲突明确反馈忙，自动扫描变更检测可继续，实际写入冲突则顺延，不制造失败提示。

扫描在槽外生成的计划不是执行授权。取得写锁后必须重验来源仍登记且启用、路径/内容与当前登记一致；启停或解除登记后不能沿用旧计划重新喂入。顺延后丢弃陈旧计划，在下一轮重新检测，不增加第二个调度器或计划持久库。

读路径仍使用既有提交快照。移除成功以后开始的读取、构建和重建不得返回或恢复目标资料；先前已开始的问答可能持有旧快照，本件不追杀所有在途模型调用。禁止旧 graph/wiki 构建在删除之后发布旧语料结果。

## D5：图谱/Wiki 失效与取消收尾

图谱 parquet 和 Wiki 是独立可读快照，仅消减检索索引不能清除其中的内容。本件在成功收尾中使旧可读图谱/Wiki 产物失效，保留可复用的抽取/摘要缓存，不自动调用模型。用户随后显式重建，图谱仍按当前剩余 Markdown 事实层推导 chunk，Wiki 使用重建后的当前图谱；不新增检索索引或 embedding 的前置条件。缓存只按当前事实层存在的 chunk 键复用，不把被删块重新注入。

HTTP/CLI 沿既有未构建语义提示重建；UI 清理旧资料清单、图谱、Wiki 与来源引用缓存，给出“图谱和 Wiki 需重新构建”提示。为了小范围正确实现，允许整体失效派生快照，不在本件新增图谱增量删边/社区重算算法。

取消在不可逆删除前可直接结束，并撤销本次尚未生效的新增确认标记及未发布暂存产物；不能撤销此前已部分执行、正在重试的确认状态。进入物理删除后，停止接受新的用户操作，但必须完成索引与快照安全收尾或保留可重试失败。不能将“文件删了一半”报为成功或正常取消。进程重启不自动清理未确认的 missing/superseded；同库写入前只恢复已确认 `user_removed` 的既定索引提交，文件删除失败仍经同一入口显式重试，不需要常驻恢复器。

## UI 与契约

资料库复用现有 Mantine 菜单、确认框、通知和进度组件。仅 `removable` 的条目提供移除，确认框展示文档名，说明保留外部原件、清除资料库内容及图谱/Wiki 需重建。失败保持目标和可重试状态；成功后刷新服务端清单与相关知识缓存。按钮忙态、键盘、读屏、长文件名与窄屏均需验收。

按 HTTP 模型导出 OpenAPI 并生成前端类型，禁止手写第二份 `source_id/removable` 契约。新增 reason 是库域内部状态；列表若显示尚未完成的移除，提供明确“移除未完成”状态，不谎称原件缺失。

## 验证

先写完整链路失败测试：正常手动导入→移除→attachments/notes/检疫副本消失→SQLite/FTS5/向量无目标→图谱/Wiki 不再可读→重建不复活；同时确认外部原件、其他手动文档、其他 tombstone 与同步登记不变。

覆盖无当前 BYOK、已换模型配置、空库、索引损坏、向量切换后 SQLite 切换前中断的无模型恢复、非法 ID/越界路径、目录同步归属、未确认、取消、文件失败、发布失败、重试、重启与 HTTP/CLI 两进程竞争。覆盖解除登记/停用后旧扫描计划不执行，以及无检索索引时按剩余事实层构建图谱。执行 golden set，检查剩余来源检索与引用未退化；对目标删除的预期变化不能通过重写基线掩盖其他来源回归。

上游锁依据：[filelock 平台文件锁与超时设计](https://py-filelock.readthedocs.io/en/latest/concepts.html)。轻依赖的具体版本与冻结收集在实施时锁定并验证；本次提案不代表互斥或移除已经实现。
