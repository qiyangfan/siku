# 设计：图谱与 wiki 生成入口界面化

## 决议

### 决议 #1：入口住址——住在视图内，不做全局工具条

生成按钮放在各自视图内：空态卡片主行动（图谱「构建图谱」/ wiki「生成 wiki」），
已建态头部次行动（「更新图谱」/「重新生成 wiki」）。与既有「重试读取」「重试」
等视图内行动模式一致，跨视图状态零耦合。

### 决议 #2：不做就绪门控，错误映射兜底

问答视图的 `ask_readiness` 判定口径 = llm 凭证可解析 **且** embedding 齐备；
图谱/wiki 生成只需 LLM 通道。复用会造成「embedding 未配但图谱本可构建」的误置灰；
新增 llm-only 就绪语义则要动内核（`model_supply`）与 settings 契约，超出本 change
边界。裁决：按钮不置灰，点击后由既有请求期错误映射（503 `llm_not_configured` 等）
给出中文指引。若后续立项 llm-only 就绪，可在本入口上叠加门控。

### 决议 #3：wiki 空态两段式引导

wiki 依赖图谱产物。空态只放「生成 wiki」主按钮；若返回 `graph_artifacts_missing`
（409），空态卡就地切换为「需先构建图谱」说明 + 「构建图谱」按钮；图谱构建成功后
**自动续跑** wiki 生成（用户意图明确：要的是 wiki）。不让用户手动二次点击，
也不预先探测图谱状态（避免额外只读请求与状态机）。

### 决议 #4：生成调用语义——幂等缓存路径，不暴露强制重建

- 图谱按钮：`POST /api/graph` 请求体 `{}`（`rebuild=false`），未变语料零 LLM
  调用，等价 `siku graph` 默认行为；「更新图谱」对已建态同样走此路径。
- wiki 按钮：`POST /api/wiki` 请求体 `{}`，本身全量幂等（`wiki 全量重建幂等`
  已是 graph-wiki spec 既有 Scenario）。
- `rebuild=true` 与 `vault/data_dir` 覆写不进 UI（serve 级参数留给 CLI/API 调用方）。

### 决议 #5：长任务反馈——同步端点 + 禁用态表达

端点同步阻塞，真实 LLM 抽取可达分钟级：生成期间按钮禁用并显示「构建中…」/
「生成中…（可能需要几分钟）」，不设前端超时；完成即刷新对应数据面（图谱：
stats+overview；wiki：清单并清空旧选中条目，防新旧内容同屏误读）。失败经既有
`ApiError` 惯例（`code/message`）在视图内展示中文 message 并保留可重试入口；
请求竞态沿用各视图既有的独立序号防抖模式。
