# 设计：非法值在各输入边界被拒，运行期只有合法状态

## D1 收口位置：边界拒绝（选）vs 让非法状态可见（否，已实现并回滚）

死路要修，但「修」有两个候选位置：

- **否**：把非法状态做进运行期的可观测面——`ask_readiness` 新增 `invalid` 字段、
  `ProtocolConfigError` 携带来源层、启动面按层决定是否容忍、设置页把坏值作为禁用项塞进
  协议下拉，使页面既出图又指出哪里非法。这一版**已完整实现并跑过门禁（744 passed）**，
  随后整体回滚。否决它的理由不是工作量，而是形状：一个本该在入口处结束的校验被摊到
  内核判定、HTTP 契约、启动策略与前端四处，每处都要新增一套状态词汇与话术；同时它扩了
  对外响应字段（`invalid`），而客户端为此要做的适配（老内核兼容、两栏话术、矛盾形状兜底）
  全部是在服务一个不该存在的情形。判据是一句话：**非法状态不该活到运行期**。
- **选**：在每个输入边界把非法值拒掉，让「配置对象」这个运行期类型只能表示合法配置。
  于是四处善后都不需要存在：读取面照常出图（因为文件层若无效就走既有的「无效文件」路径），
  就绪判定不需要新字段，启动面不需要按层分治，前端不需要显示非法值。

## D2 坏值归入哪个既有类别（归 `invalid_config_file`）

文件层坏值有两种归类：另立成因码（客户端多一个要理解的取值），或归入「这个文件对模型供给
无效」。选后者，因为对读者的出路完全相同——重新保存覆盖，或删除后重配；而 `code` 的作用正是
让客户端判断「一次保存能否修好它」。据此 `contracts/openapi.json` 的 schema/字段/路径零漂移、
UI 逻辑零改动（覆盖自救入口上一批已经建好并按 `invalid_config_file` 驱动）。

代价是 `ModelConfigFileError` 的语义从「不可解析」扩为「无效」，文案与规格措辞同步；
既有测试里断言「不可解析」字样的两处按新措辞改写（不是放宽断言，而是它确实变了）。

## D3 `detail`：服务端自撰的字段级补充，而不是回显原值

用户需要知道**哪一行**要改，把异常笼统播成「文件无效」等于没指引。两种给法：
把 pydantic 的 `msg` 原样透出（多数情况会带 `Input should be ...`，个别类型会内嵌 input_value，
而「把 key 写成未加引号的字面量」正是最常见的坏法之一，风险不可接受），或由内核自己
拼一句只含**字段路径 + 合法名单**的说明。选后者：`ModelConfigFileError` 新增 `detail`
（走 args 位置参，保住基类 `__reduce__` 的 copy/pickle 圆厂，与 `kind`/`channel` 同一先例），
它只由 `_reject_invalid_file_protocols` 产生，因此可证明不含用户原值，用例钉住
「越界值本身不出现在异常文本里」。

## D4 为什么环境变量层保留运行期检查

文件层有唯一载入点（`load_config`），环境变量没有——它按 ADR-0009 在每次合并时现读，
把校验前移到 `create_app` 会造出「启动时合法、之后 os.environ 变化就不合法」的假象，
也让嵌入式调用方与 serve 的语义分叉。因此这一层仍在通道解析处拒（`ProtocolConfigError`），
但文案改对杠杆：优先级高于文件层，页面保存覆盖不了它。这条同时销掉上一批登记的相邻缺陷。

## D5 命令行用枚举类型而不是自定义校验

`--llm-protocol` 改成 `StrEnum` 参数（三处命令共用一个类型别名），由 typer 在解析阶段
给出用法错误并列出合法值——比自己写校验更靠前、更省代码，且 help 文本自动带上候选值。
代价是枚举名单在两处出现（`LLM_PROTOCOLS` 与 `LlmProtocol`），由一条断言两者相等的用例
钉住漂移，而不是引入第三份真相。

## D6 协议文案单源到一张面一个杠杆（增量评审修正）

第一版把 `ProtocolConfigError` 的文案在 `messages.py` 内联成「HTTP 与 CLI 同一段话」，
评审时查出三处失配：`messages.py` 模块 docstring 明令 HTTP 面不得出现 CLI 参数教程、
CLI 面不得出现「设置」页，那段话把 `--llm-protocol` 放进 HTTP 面、把「设置」页放进 CLI 面；
`channel_unsupported` 说「来自启动参数」，而 embedding/rerank 根本没有对应选项；
探测面（`map_probe_error`）漏了该分支，被通用类吞成「检查 base_url、model」，
同一故障读出面给 `invalid_settings`、探测面给 `model_not_available`——两张面两个 code
正是 D4 承诺杜绝的第二套事实源。

修法是把映射抽成 `protocol_error_mapping(exc, surface)`，`map_domain_error` 与
`map_probe_error` 共用：决策依据是「哪些杠杆真的还能承载这个错误」——`llm_enum` 只剩
`SIKU_LLM_PROTOCOL`（文件层已在载入点被拒、`--llm-protocol` 是枚举参数），
`channel_unsupported` 只剩「程序传入的配置」。文案点名一个不存在或改不动的来源，
等于让用户反复去修一个没坏的地方。
