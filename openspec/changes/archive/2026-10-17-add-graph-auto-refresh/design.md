# 设计：图谱增量自动维护——授权模型、身份闸门与收尾链

## 当前证据与单一结论

内容变更后的派生物维护今天有两个收尾点：`LibraryJobManager._finish_with_index`
（HTTP 摄取/扫描/清理任务）与 `siku scan` 的收尾（cli 侧同一语义）。二者都只衔接
索引；图谱构建是独立显式入口（`POST /api/graph` / `siku graph`）。

抽取缓存键 = (chunk_id, extractor_id, model_id, prompt_version)
（`graph/cache.py`）。这给出两个事实：其一，语料未变时重建零 LLM 调用，自动增量
刷新的边际成本 = 新文档的新 chunk，与库规模无关；其二，**换模型或换 prompt 版本
会使全部缓存键失效**——显式构建时用户按了按钮、体检报告如实显示 `llm_calls=N`
（全量重抽）是知情的，而无闸门的自动刷新会把它变成一次静默的全语料重扣费。图谱
侧今天没有任何身份记录可供比对；索引侧已有对应机制（`sync_index` 的模型元数据
校验：身份不匹配 → 拒绝增量 → 指引全量重建）。

结论：默认关闭的库级开关 + 「只维护不创造」不变量 + 抽取身份闸门，全部挂在既有
任务收尾链上，自动与显式共用同一构建入口。不为自动路径新写任何增量合并/社区算法。

## D1：授权模型与「维护不创造」不变量

开关即授权，但单靠开关不能覆盖全部风险面，需要一条不变量收紧语义：

> **自动刷新只维护已存在的图谱快照；快照不存在（从未构建、或被移除/清理失效）
> 时静默跳过，首建永远显式。**

这条不变量同时解开三个结：

- **宪法红线 1**（无用户显式授权不花 key）：开开关是显式授权，首建是显式动作，
  自动路径只会为「用户自己后续的变更」花钱，且增量有上界（新 chunk 数）。
- **graph-wiki 规格**（移除后旧快照失效、SHALL NOT 自动调模型重建）：失效即不存在，
  自动路径天然够不着，不需要为自动模式开例外条文。
- **成本可预期**：用户对「维护已有图谱」有稳定心智；自动创建/自动重建属于新工作，
  超出该心智，一律留显式。

wiki 明确不进自动路径：「图已更新、wiki 待重新生成」是产品今天已接受的状态
（WebUI 本就有「重新生成 wiki」入口），把 wiki 卷进来会使授权面翻倍而收益不成比例。

## D2：开关的存储与作用域

存库域注册表的设置表，与 `scan_interval_secs` 同模式（每库一行、免重启生效、
随库走）。**不放 config.toml**：那是模型通道的机器级配置，多资料库场景下把库级
自动化偏好写进机器级文件是错的；设置中心也保持「模型通道」单一职责。

生效范围精确等于「今天已经自动维护索引的入口」：HTTP 摄取/扫描任务、CLI
`siku scan`。两个入口明确排除：

- **CLI `siku ingest`**：今天只摄取、不衔接索引（与 HTTP 导入任务行为不一致，
  是既有缺口）。在这里单独刷图谱会让图谱比索引还新，破坏「索引是图谱的检索前置」
  这一派生层次序。修复该缺口属于另一 change。
- **MCP `ingest`**：同理，且 MCP 是 AI 客户端工具面，静默 LLM 开销的可见性最差。

无 CLI 开关设置命令：跟随 scan_interval 先例（自动化偏好经 WebUI/API 设置），
CLI 只读取并遵守。

## D3：抽取身份闸门

在抽取缓存的 meta 表现有 `schema_version` 一行旁边，记录**上次成功构建**的
`(extractor_id, model_id, prompt_version)`；`build_graph` 保存产物成功后落行，
构建失败不落（产物未变则身份未变）。

自动刷新前解析当前 LLM 通道得到抽取器身份，与记录比对：

- 一致 → 执行 `build_graph(rebuild=False)`，仅缓存未命中的新 chunk 发生调用；
- 不一致 → 跳过，通知「模型/prompt 已变更，请显式更新图谱（将全量重抽）」；
- 无记录（从未显式构建过）→ 跳过（与「快照不存在」同一静默语义）。

这是索引侧「增量拒绝 + 全量重建指引」模式在图谱侧的对应物，复用而非新造。白得
的副产品：显式 `siku graph` / `POST /api/graph` 可在身份变化时预告「将全量重抽
约 N 块」（N = 语料 chunk 总数 − 当前身份缓存命中数），把今天的静默全扣费变成
知情确认。

## D4：收尾链、触发条件与失败隔离

`LibraryJobManager` 新增注入的 `graph_refresh_runner`（与既有 `index_runner`
同构：按任务现解析通道、用后关闭），收尾链扩展为 index → graph。触发条件与索引
**逐字一致**，不新造判断：非 rebuild 任务、`has_changes`、未被取消。purge/remove
走无模型消减收尾、不到这条链，因此清理后不存在「自动修复失效快照」的路径。

三处刻意分歧/边界，写进规格场景：

- **取消即停止**：取消的任务仍发布索引（既有决议：索引是已入库事实的投影，扣住
  它已入库文档不可检索），但**不跑图谱刷新**——取消表达「别再花时间花钱」，图谱
  陈旧是下轮内容变更或显式更新可自愈的中间态。
- **失败不传染**：抽取失败（限流/坏 JSON/断连/通道未配置）→ 任务仍 succeeded，
  附中文通知；旧 parquet 因原子写（临时文件 + replace）完好可读；下轮内容变更凭
  chunk 缓存续传，不重复烧已成功的 chunk。
- **成本可见**：通知携带 `llm_calls` / `cache_hits` 实际计数（体检报告已有字段），
  BYOK 信任由「花了多少」的可观性支撑。

策略本体放领域函数（graph 域）：读开关 → 查快照存在 → 比身份 → 调同一
`build_graph(rebuild=False)`，返回结构化结果（执行/跳过及原因/计数）。
`LibraryJobManager` 保持薄编排——它已是 runner 注入式架构，不为本件变厚。

## D5：产物一致性与契约

自动刷新与显式更新调用**同一构建入口、同一缓存、同一确定性合并与社区发现**，
因此产物字节级一致：「重建 diff 为空」闸门不被稀释，回归测试直接把「自动产物 vs
显式产物 diff 为空」纳入既有幂等测试文件。

对外契约均为加法：任务响应新增可选 `notice` 字段（缺失按无附加信息，旧客户端
兼容）；扫描设置响应新增 `graph_auto_refresh`（缺省 false）。OpenAPI 快照随之
刷新，diff 进评审。

## UI 与契约

开关放资料库视图自动扫描间隔旁（同一自动化设置区、同一编辑模式），文案说明三件
事：默认关闭；仅在已构建图谱时增量维护（不自动创建）；更换模型或 prompt 后需显式
更新。任务结果区在通知到达时展示中文说明（刷新计数/跳过原因/失败事实）。键盘可达、
窄屏可读遵循既有可访问性要求；不新增设置中心分区（开关是库级不是模型通道级）。
