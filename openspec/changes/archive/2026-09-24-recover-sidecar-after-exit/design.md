# 设计：桌面壳管理运行期恢复

## 方案

sidecar 健康检查通过后，由 Rust 后台监视器定期检查已托管子进程是否退出，以及 `/api/health` 是否持续无响应。连续五次检查失败后视为服务不可用，停止旧进程并将窗口导航回壳内置状态页。监视器不自动拉起新进程，恢复页显示原因并等待用户点击。

状态页通过 `recovery=1` 区分运行期恢复状态与首次启动状态。恢复页的重新启动操作移除该标记并重新加载壳页；现有 `on_page_load` 编排随后回收残留 sidecar、启动新进程并执行原有健康检查。成功后窗口再次导航到 sidecar 同源 UI。启动失败页的“重新启动本地服务”操作也使用同一启动编排。

React 共享页头每 10 秒检查一次 localhost 健康状态，在全部视图显示“服务正常 / 服务未连接”；离线说明也位于共享框架，切换到资料库或设置时仍可使用“检查连接”。浏览器/Vite 页面在 API 不可用时展示启动命令，因为它既没有，也不应获得系统进程控制能力。桌面壳的启动/恢复页才提供真正的进程重启按钮。

## 失败与竞态

- 监视器只管理与创建它时相同的启动代际；用户已发起新一轮启动或正在关闭窗口时，旧监视器退出。
- 进程正常运行但 HTTP 健康接口短暂失败时，连续失败计数清零，避免一次网络抖动触发恢复流程。
- Unix 平台用独立进程组优雅关闭并在超时后强杀整个进程组；Windows 将 sidecar 纳入带 `KILL_ON_JOB_CLOSE` 的 Job Object，释放 Job 句柄时收回仍存活的后代。
- 连续五次失败后先回收托管进程及后代，再显示恢复页，避免重启与旧服务争用端口。
- 启动健康检查仍沿用既有超时、日志和健康响应身份校验，不改变 API 合同。

## 验证

- Rust 单元测试覆盖恢复 URL 构造、查询参数识别与边界情况。
- 桌面壳测试通过后，验证启动→健康→模拟服务退出→恢复页→手动重启→健康→UI 的恢复链路。
- React 测试验证离线卡片按钮只检查连接且文案与 CLI 手动启动指引一致。
